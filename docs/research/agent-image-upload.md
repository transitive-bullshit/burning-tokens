# Direct agent image upload compatibility

Research checked 2026-09-30. These findings describe transport options, not a claim that every ChatGPT mode supports them.

## What GET can carry

Cloudflare's Workers `Request` API explicitly prohibits a body on `GET` and `HEAD`. An origin accepting such bodies would still depend on client and intermediary support. RFC 9110 assigns no general semantics to GET content and warns against relying on private agreements across intermediaries. Supporting a GET body therefore cannot make a URL-only reading tool transmit a file. [Workers Request](https://developers.cloudflare.com/workers/runtime-apis/request/), [HTTP semantics, GET](https://httpwg.org/specs/rfc9110.html#GET).

Cloudflare documents a 16 KB URL limit. Base64 takes four characters per three bytes, so even before the path, capability and metadata, one URL carries less than 12 KiB of decoded image data. One intentionally mutating GET can support tiny optimized images; staged GET requests can transfer larger images in parts. Cloudflare's minimum documented request-body limit is 100 MB, well above Studio's own 2 MiB limit. Raising Cloudflare upload limits would not resolve either restriction. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/).

RFC 9110 recommends support for URIs of at least 8,000 octets. An 8 KiB decoded part expands to 10,923 base64url characters before metadata, exceeding that baseline despite fitting Cloudflare. Prefer a configurable part size with a 4 KiB default and 8 KiB ceiling, or another way to restart with smaller parts. No official ChatGPT web-reader URL-length limit was established. [HTTP URI length](https://httpwg.org/specs/rfc9110.html#uri).

Staging removes the single-URL total-size restriction, provided the agent can read and encode the file. Bind each upload to declared size, MIME type and full-file SHA-256; use indexed, immutable parts, duplicate-safe writes, resumable status and explicit commit through the existing artifact pipeline. Bound outstanding staging bytes, part count and lifetime. A 2 MiB file needs 256 parts at 8 KiB or 512 at 4 KiB, plus setup/commit requests; these are arithmetic costs, not measured client limits. Optimization before encoding matters. This is a compatibility protocol, not HTTP multipart/form-data.

A GET-triggered **source URL import** is also implementable: the agent supplies a fetchable HTTPS image URL in the query and the Worker downloads the bytes. This is an architectural inference from ordinary Worker subrequests, not an OpenAI promise. It avoids placing the image bytes in the request URL, but requires an existing remotely reachable URL. A `sandbox:/mnt/data/...` reference, local file path, or bare OpenAI file ID is not such a URL. Neither a URL import endpoint nor Cloudflare settings can extract inaccessible sandbox bytes on their own.

## Established ChatGPT file bridges

Custom GPT Actions support `openaiFileIdRefs` in a POST request. ChatGPT replaces these references with objects containing `name`, `id`, `mime_type` and `download_link`. The links last five minutes; Actions can send uploaded files, generated images and Code Interpreter files. This requires a configured Action available in that session. Merely publishing an endpoint or OpenAPI document does not add the Action to an ordinary ChatGPT conversation. [Sending files with GPT Actions](https://developers.openai.com/api/docs/actions/sending-files), [Actions introduction](https://developers.openai.com/api/docs/actions/introduction).

The current OpenAI plugin/MCP reference supports file inputs through `_meta["openai/fileParams"]`. A declared file schema includes `download_url`, `file_id`, `mime_type` and `file_name`; only the first two are required. ChatGPT supplies a temporary URL to the tool. Widgets can request a fresh URL for an authorized file with `getFileDownloadUrl`. This is another integration requiring an available tool, not a capability of a plain website GET. The reference does not establish that every generated image in every ChatGPT mode is automatically available to every plugin. [Plugin file APIs](https://developers.openai.com/plugins/reference#file-apis).

## Complementary direct-agent options

| Route | Practical benefit | Required capability and boundary |
| --- | --- | --- |
| Browser file form | One browser POST avoids hundreds of GET parts when shell networking is unavailable. | A computer-use agent must be able to attach the actual file. Playwright supports file paths and in-memory buffers through `setInputFiles`; a tool without that capability does not acquire it from an HTML form. [Playwright uploads](https://playwright.dev/docs/input#upload-files). |
| Same-origin browser JavaScript | Once bytes or a `File` are available, a small script can call the existing raw-body POST endpoint and read its result. A base64 textarea can also let an automation agent supply bytes without a file picker. | This is an implementation inference. The browser tool must permit JavaScript or form entry and possess the bytes. Ordinary page JavaScript cannot select a local file by assigning its path: the HTML standard rejects nonempty file-input `value` assignments. [HTML file input API](https://html.spec.whatwg.org/multipage/input.html#dom-input-value). |
| Pull an existing download link | One import request can transfer an image already hosted somewhere reachable, without copying base64 through model context. | The agent needs an authorized direct download URL, not a preview page or sandbox reference. Dropbox documents `dl=1`/`raw=1` and redirects; supporting such providers needs explicit redirect validation and host policy beyond an OpenAI-only importer. [Dropbox download links](https://help.dropbox.com/share/force-download). |
| Action or MCP file bridge | Lets the ChatGPT host provide a temporary file URL, avoiding manual download/reupload and model-carried image bytes. | Requires the configured integration and file access in that session; see the official mechanisms above. |

After staged GET support, a browser upload form with an optional base64 entry is the smallest complementary path for browser-capable agents. A dedicated Action/MCP bridge is the stronger next investment for standard ChatGPT file workflows. Add URL imports when a real client supplies a supported downloadable URL. None of these routes can transmit bytes unavailable to every tool in the session.

## GET caching and privacy

GET mutations intentionally depart from safe-method semantics. Crawlers and prefetchers can follow GET links; keep mutation templates out of ordinary navigation and require explicit operation intent. [HTTP safe methods](https://httpwg.org/specs/rfc9110.html#safe.methods).

Return `Cache-Control: private, no-store` on success, progress and errors. `no-store` prohibits compliant HTTP caches from storing the request or response; the standard explicitly says it is not sufficient to ensure privacy. It does not remove browser history, application logs or tool transcripts. [HTTP caching](https://httpwg.org/specs/rfc9111.html#cache-response-directive.no-store). Use `Referrer-Policy: no-referrer` on HTML upload/status pages so subsequent navigation does not send their URL as a referrer. [Referrer Policy](https://w3c.github.io/webappsec-referrer-policy/#referrer-policy-no-referrer). Do not log capability paths, image queries or signed download links, and do not cache staging routes. Stable idempotency plus full-file verification must make retries harmless.

## Recommendation for this repository

Keep raw-body POST as the primary direct upload, with bounded single-GET and staged GET transfer for clients that can read and encode files but cannot POST. Advertise each transport's precise limits and optimized JPEG/WebP requirement. Do not describe a sandbox path as importable or claim upload success until the response contains a ready artifact.

For any intentional GET mutation, require the existing private capability, an explicit upload operation and idempotency key. Keep ordinary GET listing and HEAD nonmutating, preserve no-store responses and sensitive URL handling, and route through the current upload validation, room/lifecycle gates, moderation and owner event path. At the time of inspection, `RetreatSession.handleStudio` skipped events for GET, and its room/lifecycle mutation checks depended on method; implementing GET writes only inside `RetreatStudio` would bypass those protections.

For source imports, the exact host `files.oaiusercontent.com` appears in the Actions download-link examples. The plugin reference uses an unspecified `https://...`, which does not establish additional permitted hosts. A narrow initial implementation can allow only `https://files.oaiusercontent.com` on the default port, reject embedded credentials and all redirects, limit duration and streamed bytes, and never forward visit credentials or cookies to the source. Do not infer a wildcard allowance for all OpenAI-related domains. Reuse byte-signature validation and the existing publication rules. Treat signed source URLs as secrets. This is implementation guidance, not a recommendation to relax general edge security settings. [Documented download-link example](https://developers.openai.com/api/docs/actions/sending-files).

Request optimized JPEG or WebP before transfer and conversion of unoptimized PNGs. Server-side conversion is possible after bytes arrive: Cloudflare's Images binding accepts raw streams and supports WebP/JPEG output with quality settings. It adds a binding and billed transformations; it does not solve sandbox egress. [Images binding](https://developers.cloudflare.com/images/optimization/binding/).

Focused regression coverage should exercise a real small optimized image, duplicate retry, conflicting idempotency key, malformed/oversize payload, MIME mismatch, closed visit, wrong room, owner event delivery, private/moderated audience and a read-only ordinary GET/HEAD. Staging adds missing/out-of-order/conflicting parts, resumability, byte/hash mismatch, expired state and duplicate commit. Import support additionally needs redirect, timeout and source-size tests with mocked upstream responses. No stress or capacity testing is needed.
